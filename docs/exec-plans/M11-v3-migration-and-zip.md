# M11 普通 ZIP、首次发布基线和 v3 迁移

所有者批准按当前功能定义 v4 首次发布基线，并明确要求移除未发布的格式和设计。正式安装、更新及发行归 M12。迁移器使用独立路径构建，发布的 Core、GUI、CLI、MCP 和 SDK 不依赖旧数据解析器。

## 首发合同修正

ALCOMD 自有合同首次发布前只有一份有效定义，版本号始终为 1，破坏性变更也原位修订。输入只按现行结构校验；相同结构具有相同语义。禁止旧合同专属识别、别名、迁移、回退或拒绝分支。GUI、CLI、MCP 具备相同业务权限；认证、撤销、实际调用者和资源归属由 Core 检查，扩展遵守自己的沙箱和授权。

## 普通 ZIP 和绝对路径

- `backups.create` 协商 `backups.create.v1`，根据项目 ID、revision、已有内容选项和幂等键提交任务。`destinationPath` 可指定绝对 ZIP 文件名，省略时采用 Core 中设置的目录与命名策略。
- `backups.restore` 协商 `backups.restore.v1`，接收 Core 主机上的 `archivePath` 和幂等键。可传 `projectName` 自定义默认项目根中的目录名，或传 `destinationPath` 指定尚不存在的绝对项目目录。默认建议名来自 ZIP 文件名。两方法返回 `operationId`、`replayed`，文件或已登记项目在任务成功后可用。
- 解压前检查 ZIP 根部的 Unity 工程结构、条目路径、类型与配额。源文件、目标父目录和发布位置受身份复验、同卷暂存和独占发布约束。无效 ZIP 统一按当前根结构判断。项目已经存在时保留原目录。
- MCP 项目登记、创建和复制接受绝对路径。备份使用 `alcomd_create_backup` 和 `alcomd_restore_backup`，恢复继续要求确认。现有身份、权限和撤权检查继续执行。路径始终指 Core 所在主机，任务响应与普通错误保持脱敏。

GUI、CLI 和 MCP 的入口、对应 Core 用例及自动化测试见[绝对路径对照表](../testing/M11-absolute-paths.md)。

## 首次发布数据基线

- State1 由一份初始 DDL 直接创建。已存在的数据库按当前标识、版本和结构识别，输入未通过现行结构校验时，在启用 WAL 或恢复前保全原文件。
- 生命周期和数据边界见 [State1](../../specs/storage/state-v1.md) 与 [Config1](../../specs/config/settings-v1.md)。
- Config1 使用当前完整 JSON/TOML 合同中的生效字段。设置按现行 TOML 文档读取和写入。Core 在打开数据库后执行持久任务恢复，打开任何一侧前同时预检数据库与配置。
- 已撤销的备份登记、归档清单、恢复计划、MCP 逐路径审批、开发数据升级和旧模板文件自动清理从生产路径移除。删除旧恢复计划遗留的未使用错误名，并同步 RPC、MCP 和派生项目工具 Schema。保留通用任务、幂等回执、项目登记及恢复所需的文件系统日志。
- 公共变更影响测试期 v4 客户端和数据。协议 major 仍为 1，ZIP 和 MCP 工作流通过更新后的 capability 协商。

## v3 迁移和删除边界

所有者批准用隔离候选验收数据迁移健康检查、提交与恢复。正式产品安装包、更新源部署、正式 DEB 包管理器交接、卸载和发行归 M12。

- 以冻结的 ALCOMD3 3.4.0 为直接迁移源。Windows 的用户级与机器级部署分别验收，各系统用户的数据各自迁移。macOS arm64 和 AppImage 保留 v3 可启动状态直至独立 bridge 提交。DEB 交接由包管理器完成。
- 项目、Unity 安装与启动参数、仓库、模板、设置和扩展偏好由迁移器映射到现行字段。含认证仓库的完整导入需要明确授权将凭据转移到系统凭据库。新 Core 不导入旧 MCP 密钥或授权。外部 MCP 的隔离补丁需要冻结版快速设置前后配对快照与确认摘要，逐字节保留无关配置并可回滚。真实配置仍需要具体实例的归属证据和授权。活动与技术日志排除在数据包之外。保留现存的项目和备份目录，未创建的目录使用 v4 默认位置。
- Bootstrap 对恢复源、健康检查、提交点和中断恢复写持久记录。提交前的失败应能恢复到 v3 可启动状态。提交后只可清理清单中经过验证与另行授权的确切实例。现有 [v3 实例清单](../../migrations/v3/artifacts.toml) 保持观测和审批证据，未确认条目保持原位。
- 本机 bridge 校验签名载荷并在同卷暂存目录完成导出、导入、Core 重开对账和独占发布。发布之前还需要绑定候选载荷与安装范围的签名平台验收报告。用户侧重新验证数据包和本地状态摘要，无须逐账号签名。开发构建使用合成密钥测试失败路径和恢复，正式签名材料另行授权。
- `alcomd-import` 只定义当前原生数据包。Core 依赖此类型包和已有 SHA-256 实现。独立迁移器复用平台的无链接读取、持久写入和当前用户凭据库。Bootstrap/Updater 复用平台的路径身份、目录持久化和原子发布。依赖均来自整仓现有锁定版本，避免重复实现平台校验；模块边界由 `cargo xtask check` 验证。
- 选择性导入使用同一原生 SDK 向运行中的 Core 提交明确选择的内容。支持 VCC 与旧 ALCOM 的项目、Unity 登记、无认证仓库和本地包，以及三个来源的已识别设置、主题和模板。模板申请绑定源内容摘要，存档转换产物使用固定暂存目录恢复同键操作。已有不同内容的同标识模板保持原样。官方 VCC 和旧 ALCOM 生成的默认资料已复验，专用 `ALCOM` 目录和 ALCOMD3 2.1.0 Beta 已按获批的自制样本补验。通过既有用例复用幂等、revision、路径校验与现有记录保护，无需新增公共方法。
