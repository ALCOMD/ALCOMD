## 当前有效读取合同

- GUI 在正常的软件包候选请求中取得 Core 读取的项目信息，不先调用 projects.refresh，不填充数据库，也不新增独立提示、补采按钮或后台填库流程。保留 100ms 首屏预算，慢请求仅延后包列表。
- Core 在授权、项目 scope 和请求/revision 校验后，通过现有有界项目读取器获取项目清单、当前锁定版本与本地 package.json。文件是本次展示信息的来源；候选查询不修改项目、项目登记快照、revision、事件或操作日志。
- 新的普通首读重新读取项目文件。搜索、版本选择和分页可使用本次结果的内存快照，按 Principal/Project/登记 revision 隔离；仅保留一份、受既有 4096 包/16MiB 上限约束。新首读观察到变化会改变候选指纹，旧 cursor/expectedSnapshot 被拒绝。内存丢失可重新读取并校验指纹，不写持久副本。
- 登记记录修订仍由既有项目用例持有，文件观测另外进入候选 fingerprint；既有 Plan/Apply/recovery 的冻结授权与文件过期检测保持，不以展示读取改写它们。
- 保留来源关闭/缺失等价、已安装事实、名称/说明/关键词/别名、合法链接、撤回提示、SDK/legacy 展示取舍、精确来源、安装样式和 Core Unity 分组。

## 仓库索引自动刷新（2026-11-08 后续授权）

所有者随后明确要求保留查询与刷新分离，但查询需要触发自动刷新，不能只依赖手动刷新。本项取代 M3 原有“仅显式刷新”限制；候选查询本身的只读、权限/scope、分页快照和冻结 Plan/Apply 合同保持。

- 本机已授权的仓库 list/get/packages 和项目候选查询成功后，仅通知 Core 后台维护任务；无效或未授权请求不触发刷新。响应不等待网络，首屏使用已有索引。
- Core 合并并发通知，延迟500ms避开首屏，按上次成功观测的5分钟时效筛选仓库；失败尝试也以5分钟内存间隔限频，不后台持续轮询。关闭仓库不自动刷新，手动刷新仍立即执行。
- 自动维护以 Core 自身 authority 调用现有刷新用例，保持 HTTP 条件请求、并发上限、凭据读取、资源锁、完整解析后原子提交、revision/Event 和失败保留旧索引。锁内重新检查新鲜度，避免排在手动刷新后重复联网。
- 使用现有 repository 事件通知页面重查；无新增公共 RPC、权限、数据库结构、生产依赖或项目展示持久副本。Core 退出时取消并回收后台任务，不脱离进程生命周期。
- 已验证过期/新鲜/关闭仓库、并发合并、失败限频与旧索引保留、手动刷新不受时效限制、实际 RPC 先返回缓存后发布刷新事件，以及无效请求不产生网络访问。209项受影响 Rust 回归通过、1项既有忽略，严格 Clippy/检查/构建通过，Core 已更新、GUI 沿用原构建与 profile 重新打开；详见[验证记录](../testing/repository-auto-refresh-20261108.md)。所有者已授权本地提交；未推送，H7 保持。
