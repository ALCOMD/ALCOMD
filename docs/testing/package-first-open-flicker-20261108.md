## 观察与原因

原生GUI使用原数据/profile重新启动，Core保持PID269324。通过获准的Computer Use取得首次点击管理后的20张连续截图：旧项目页、管理页页头/工具栏、完整列表依次出现；页头控件在初次布局中发生变化。该桌面接口的采样间隔约115–180ms，点击调用约207ms后返回，因此这些截图不能证明捕获了每个短暂原生帧。

随后对同一GUI前端进行浏览器合成帧录制，使用与实际页面相同的29包规模及4倍CPU限速放大首次路径。以点击为起点，修复前约236.2ms才创建primary页面读取，已经错过100ms等待预算；读取就绪后仍观察到整页fallback。39张合成帧中，主体区域像素采样有28帧完全为空白。这解释了首次渲染较慢时会出现的整块闪动路径；此前仅依据RPC约10–40ms或低频截图不能确认这个原因。

原实现只在延后渲染的目标组件挂载时启动读取；100ms截止逻辑独立运行。首次组件构建推迟了读取启动，截止后Suspense先提交空白主体，再呈现内容。另一个首帧不稳定点是Select的文字和收缩布局在普通effect中更新，可能在已经绘制后改变页头宽度。

## 实现

- 在已知权限的项目管理导航动作中启动原有只读用例；仍使用CoreEvents的一致性读取及同一访问的primary槽，组件挂载时复用同一请求。
- 访问槽保存已完成结果，首次组件同步消费就绪值，避免React为了首次观察一个已完成Promise而再次挂起。最多仍为三个读槽，不跨访问、连接或项目复用，不持久化数据。
- Select的文字/收缩布局准备前移到layout effect，沿用Material公开选择接口及原有适配样式。
- 导航的`deferUntil = performance.now() + 100`、截止定时器、慢元数据整页加载和慢候选只延后列表的规则保持。未增加最短加载时长、额外延迟或更长等待。

最终同条件合成帧对照中，读取在点击后约4.7ms启动，32帧的主体均有内容，没有整页空白采样。这里的100ms是既有异步等待预算；CPU限速下的整体首次控件绘制仍可能超过100ms，本轮不把所有渲染耗时描述为100ms内完成。
