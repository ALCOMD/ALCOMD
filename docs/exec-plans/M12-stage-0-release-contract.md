## 2. 安装布局与程序所有权

| 格式 | 正式布局 | 入口和权限 |
| --- | --- | --- |
| Windows Inno EXE | 当前用户默认 `%LOCALAPPDATA%\Programs\ALCOMD`，所有用户默认 `%ProgramFiles%\ALCOMD`。获准自定义时保留解析后的真实安装根。内部载荷位于 `runtime\<version>`，每个根发布一个活动版本。 | `bin\alcomd-cli.exe` 为唯一加入 PATH 的公开入口，GUI 快捷方式和 `alcomd://` 指向同一受控布局。当前用户写对应用户区域；所有用户只在显式选中时提升，写机器区域。迁移和凭据操作在目标登录账号下执行。 |
| Linux AppImage | 用户自行保管 AppImage。本机为冷启动将经过签名清单核验的运行载荷放入 `$XDG_DATA_HOME/alcomd/runtime/<version>`，未设置 XDG 时用 `~/.local/share`。 | `~/.local/bin/alcomd-cli` 由用户显式启用。登记指向持久目录，便携本体用同目录中的受控归属记录绑定。 |
| Linux DEB | 公开命令为 `/usr/bin/alcomd-cli`，程序由包管理器管理在 `/usr/lib/alcomd/runtime/<version>`，标准桌面入口也由包管理器拥有。包名提案为 `alcomd`。 | 系统安装、更新、移除经 `apt/dpkg` 执行。维护脚本只管理包拥有的系统资源。每用户的 Core 初始化、凭据、数据迁移由用户身份下的 Bootstrap 和 Core 完成。 |
| macOS arm64 DMG | 通过 DMG 将 `ALCOMD.app` 拖入 Applications。`Contents/Resources/runtime/<version>` 放置内部载荷，应用自己的入口从当前 bundle 解析。 | 用户显式启用后建立 `~/.local/bin/alcomd-cli`，拖入时保持 shell 配置现状。重定位、移除与原生验收在恢复 Mac 阶段核对。 |

Windows 两范围使用共同的产品安装互斥。准备顺序先锁机器安装操作，再锁发起账号和受影响实例的程序接入。范围转换先核对已登记程序路径、作用域与所有权，显示实际会切换的入口。其他账号仍运行 Core、另一个安装根或关联归属无法确认时，返回可重试的阻塞结果。管理员账号和发起迁移的账号不同时，分别校验 SID，机器部署阶段不写管理员或其他账号的资料目录。DEB 与 AppImage 之间按实际程序和入口所有权处理冲突，包管理器的路径由包管理器处置。

系统入口拟覆盖已批准的 `alcomd://repositories/add` 和 `alcomd://extensions/add`，以及仓库清单、模板、扩展包的应用内导入入口。文件关联启用前逐项验证冷启动将输入送到实际的确认流程。没有已批准并可验证的打开流程的格式不登记关联。CLI、关联与快捷方式拒绝未经校验的路径及安装参数。

### 登记、提交与恢复

1. 按平台安全打开安装根和目录。记下产品、范围、版本、实例、程序身份以及之前生效的入口。检查待写区域是否同卷并可持久化，检查数据目录、运行目录、文件及父路径的所有权、链接、重解析点和权限。
2. 复用 `core-installation-v1` 的一行 UTF-8、LF 结尾规范绝对路径格式。Bootstrap/平台适配器将它作为每账号入口指针，通过同目录暂存、文件同步和原子替换发布。旧登记和入口快照记入对应事务。相对路径、远程 Windows 路径、非规范路径或所指程序失效时返回可处理的错误。
3. 无登记的普通安装用户从已部署、可验证的官方 GUI 或 CLI 入口初始化。入口用当前产品实例和受控程序目录启动 Bootstrap，Bootstrap 调用 Core 完成初始化和健康检查，再发布该账号的登记。现有独立 SDK 客户端延用登记读取器、同账号 IPC 与 5 秒就绪预算。未登录账号可在下次使用官方入口时补齐。
4. AppImage 持久运行目录中的 `portable-origin-v1.json` 由 Bootstrap 写入，记录 `schema`、`appImagePath`、`appImageSha256`、`payloadManifestSha256` 和经过完整验证的文件身份。冷启动须重新打开便携本体并核对归属、设备、inode、大小和变更时间。缺失、移动、换向或身份变化时返回可处理的失效错误，由用户从可信位置启动并完整复验后重新绑定。用实包测冷启动耗时，准入使用原 5 秒预算。
5. 共用持久阶段为准备、停止旧组件、暂存、健康核对、提交意图、入口发布、清理。同版本目录与候选摘要不一致时拒绝覆盖。一个事务只选择一套完整程序。提交意图前异常恢复原可启动套件、入口与允许恢复的数据。提交意图后优先完成同一已验证事务，只有对应程序和数据配对已核实时才能恢复旧版。故障注入逐阶段核对没有两代 Core 同时写同一份状态。卸载后如果其他账号仍留有登记，已移除实例必须无法冷启动。

## 3. v4 更新声明与旧版入口

v4 自更新使用 `GET /api/v1/product-updates/{channel}/{target}/{format}.json`。生产站点仍由现有产品身份与发布权限决定。Windows Inno、AppImage、DMG 分别使用 `inno`、`appimage`、`dmg`。DEB 从签名发行清单与包管理器获取版本、摘要和包，v4 Updater 可报告途径。独立带签名的清单用于人工核对下载的完整产品。构建清单、供签名的准确字节和正式外部资产清单分别生成，健康证明及外部资产摘要可关联同一候选且不需要自引用。

- `200 application/json` 返回 `manifest` 与 `signature`。`manifest` 是 UTF-8 JSON 准确字节的无填充 base64url，解码后最多 32 KiB。整个 HTTP 实体最多 64 KiB。`signature` 是 128 字符小写十六进制，验证 Ed25519 签名消息 `ALCOMD product update manifest v1`、一个 NUL 字节和 manifest 解码后的原始字节。使用构建时确认的公钥。签名通过后按 Schema 与运行时语义严格校验，重复键拒绝。已有 v3 Minisign、桥接载荷及健康证明继续各用其已批准的签名域。[v4 更新声明 Schema](M12-update-manifest-v1.schema.json)
- 目标、格式、频道及产品必须匹配当前安装和请求。`stable` 仅提供稳定版本。`beta` 可提供稳定或预发布版本。切换由用户明确选择且保持目标版本严格大于当前版本。解析完整 SemVer，发行版本采用规范形式。资产名按产品、版本与目标派生和核对。下载前核对 HTTPS、获批主机和重定向，下载后核对尺寸和 SHA-256，执行前再验证文件和载荷身份。v4 下载上限提案为每资产 512 MiB。
- 每个频道、目标与格式使用独立正整数 `serial`。记录最近验收的序号与声明摘要，同序号重复读取应得到相同字节，较旧序号拒绝。`issuedAt` 和 `expiresAt` 使用 UTC 秒精度，有效期最多七天，签发时间最多允许五分钟的时钟偏差。`204` 表示本次无更新，保留已记录的序号与本机版本。暂停推送可使用获批的无更新响应，正常更新拒绝降级，程序恢复按已有事务证据执行。
- 冻结 v3 stable 与 beta 的请求路径、资产名、大小配额、验签、白名单启动参数继续按原客户端验收。Windows 旧 feed 只提供获批桥接候选，保留原安装范围，超过旧下载上限时另议 WebView2 离线方案。冻结 Mac/AppImage 不从旧自动更新源取得原位替换的 v4 包，独立 bridge 先保留可启动 v3。DEB 由包管理器交接。正式上线前核对旧新域名的同频道交接与按请求平台隔离的 HTTP 缓存。[冻结更新 API](../baselines/update-api.md)
