# M7 删除目录未移动时的明确失败

2026-11-10 所有者报告删除任务长期不结束，并明确要求“如果因为占用导致失败应该明确返回失败而不是等待”。继续原删除意图，等待正常退出实际占用目录的 Unity Hub；不关闭另一个项目的 Unity Editor，不直接改库或绕过 Core 删除。

## 已确认原因

当前任务 da9ef751-4c88-466f-b3a0-0b956c733202 在 quarantine_intent 后进入 recovering/recovery_required。原目录存在，payload 不存在，Windows 只读共享检查返回32；目录句柄持有者属于 Unity Hub 及其服务。Core 对 intent 后的一切失败强制恢复，但仅启动时恢复；业务日志又丢弃恢复失败的具体原因。

## 实施合同

- 保留 intent 的 durable 写入及已隔离目录的 forward-only 恢复；不把 intent 提交等同于目录已经移动。
- rename 明确失败后，只有复验原 root identity、payload 不存在、此前未观测到 quarantine identity 时，可信文件系统 adapter 才可证明 source 未移动。Core Store 只在 intent/原恢复阶段且无 quarantine identity 时接纳此证明，记录 failed/completedAt，保留项目登记/内容及完整 journal；空准备目录尽力清理，单独的准备清理失败只补充诊断，不把未移动项目重新放入删除恢复；之后不会在重启时重试该终态任务。需用户显式重新发起删除。
- 失败沿用既有 project_delete_source_unsafe 与原始 OS 错误/路径诊断，不新增公开 RPC 形状、错误码、权限、数据库或依赖。原始错误在日志保留。
- 已移动目录、状态不明、目标冲突，继续保留恢复合同，不伪报失败完成；真实停止的恢复错误记为 Waiting 并保留错误详情，实际恢复执行仍记 Started。
- 修复前用 Windows 不共享 DELETE 的真实目录句柄复现；修复后证明 failed、项目/标记/登记保持、wrapper 清理、日志包含 os error32、重启不再删除；继续既有真实删除、占用复验、取消与 kill/restart 矩阵。

本项接续当前 M7。前一轮仓库解析/State32 未提交修改保持；无提交/推送或程序替换授权。真实任务仅经现有 Core 的原恢复路径处理，不通过文件工具递归删除用户项目。
